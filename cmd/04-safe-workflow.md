# Agent 指令：Android 多模块项目安全执行流程

这个文档给出一套推荐的 Agent 分阶段执行流程。  
适合对已有项目进行文档补齐、依赖检查和后续重构规划。

---

## 为什么要分阶段

不要一上来就让 Agent 完成整个架构改造，因为风险较高：

- 可能误判模块职责
- 可能错误移动代码
- 可能修改 Gradle 后导致项目无法编译
- 可能删除已有文档
- 可能把业务逻辑错误下沉到公共模块

推荐分阶段执行：

```text
第一步：只分析项目结构
第二步：生成 docs 文档
第三步：检查 Gradle 依赖风险
第四步：人工确认后再考虑重构
```

---

## 第一步：只分析项目结构

使用指令：

```md
先不要改代码，请只分析当前 Android 项目的多模块结构，并给出模块分类、依赖风险和文档落地建议。
```

期望产出：

- 当前模块清单
- 模块分类建议
- 依赖关系总结
- 风险点
- 后续建议

验收重点：

- 模块分类是否符合项目实际情况
- 是否把业务模块、支撑模块、工具模块区分清楚
- 是否明确标注了不确定项
- 是否没有修改任何文件

---

## 第二步：生成 docs 文档

使用指令：

```md
请根据刚才的分析结果，开始落地 Android 多模块架构文档。

只允许新增或修改 docs/ 目录下的以下文件：

- docs/README-module-index.md
- docs/module-architecture.md
- docs/dependency-rules.md
- docs/module-template.md

禁止修改业务代码、Gradle 配置和模块结构。
```

期望产出：

- 模块架构说明
- 依赖规则说明
- 新增模块模板
- 文档索引

验收重点：

- 文档是否使用真实模块名称
- 不确定的模块是否标注“待补充”
- 是否没有修改业务代码
- 是否没有修改 Gradle 配置

---

## 第三步：检查 Gradle 依赖风险

使用指令：

```md
请检查当前 Android 多模块项目的 Gradle 依赖关系，并输出依赖风险报告。本轮只分析，不修改代码。
```

期望产出：

- 当前依赖关系表
- 合理依赖列表
- 可疑依赖列表
- 明确违规依赖列表
- 调整建议

验收重点：

- 是否识别 business 直接依赖 business
- 是否识别 support 依赖 business
- 是否识别 libs 依赖业务模块
- 是否识别 app 壳工程过重风险
- 是否给出分级风险

---

## 第四步：人工确认后再考虑重构

只有当前三步都确认无误后，才考虑让 Agent 执行重构。

重构前建议先让 Agent 输出计划：

```md
请基于前面的分析结果，给出模块依赖治理的重构计划。

本轮仍然不要修改代码，只输出计划。

计划需要包含：

- 需要调整的模块
- 需要新增的 api 模块
- 需要移动的类
- 每一步的风险
- 每一步的回滚方案
- 建议的提交拆分
```

确认计划后，再按小步提交执行：

```md
请只执行重构计划中的第 1 步，不要执行其他步骤。
完成后输出修改文件列表和验证建议。
```

---

## 推荐提交拆分

如果后续真的要改项目，建议拆成多个提交：

```text
commit 1: docs: add module architecture documents
commit 2: docs: add dependency rules and module template
commit 3: refactor: introduce api-user module
commit 4: refactor: replace direct user module dependency
commit 5: refactor: clean app business logic
```

不要把文档、Gradle 修改、代码移动、业务逻辑重构混在一个提交里。

---

## Agent 使用原则

建议给 Agent 加上以下通用限制：

```md
除非我明确授权，否则不要修改代码。
除非我明确授权，否则不要修改 Gradle。
除非我明确授权，否则不要移动或删除文件。
如果你不确定，请标记为“待确认”，不要猜测。
每次执行前先说明计划，每次执行后列出变更清单。
```

---

## 总结

最安全的方式是：

```text
先看清楚
再写文档
再查依赖
最后才重构
```

Agent 可以帮助提升效率，但架构边界和模块职责最好经过人工确认。
